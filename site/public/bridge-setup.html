Bring your own working environment.

The bridge runs on the computer that owns your tools. It receives authenticated requests from your server, runs fixed owner-approved actions, and returns results. A laptop tool remains manual-only; connecting it does not make it available when the laptop is off.

Recommended: pair an outbound laptop agent

Open Connections → Pair / manage a computer in your workspace. Name the device and create its one-time token. Run the displayed Windows PowerShell installer command on that laptop; it prompts privately for the token. Python 3.10+ is required. No inbound port, VPN or laptop certificate is needed.

Inspect / download the Windows installer · Outbound Python agent

-FullControl enables account-level Python, PowerShell, CMD and file access. It does not elevate privileges. Desktop Office uses installed Excel/Word in your logged-in Windows session. Without full control only configured actions/source inspection are available. Revoke the device in Connections or stop the TH Personal Device Link startup task to disconnect it. A running command cannot be undone by revocation.

For macOS/Linux, download both Python scripts into one private folder, create a device.json with your HTTPS server origin, one-time token, execution: "desktop", fullControl: true, roots: {"home": "/your/home"} and actions: {}. Restrict this folder to your account and run python3 personal-device.py --config device.json. Device permissions are those of the account running it.

Alternative: an existing HTTPS bridge

1. Install once on each participating computer

Use Python 3.10 or newer. Edit a configuration example with the actual allowed folders and executable/script paths. Commands are fixed in this file; workflow input arrives as JSON on stdin, never as an interpolated shell command. Your scripts should return JSON on stdout.

Run the service as your chosen account with the filesystem/device permissions your tools need. Configure requiresDesktop: true for tools depending on a GUI, logged-in Office session or local-only device.

2. Configure authenticated HTTPS

Set a unique private TH_COMPANY_BRIDGE_TOKEN (at least 32 random characters), TH_COMPANY_BRIDGE_CERT and TH_COMPANY_BRIDGE_KEY in the service environment. The certificate must be trusted by the RPI server and match the endpoint hostname. Keep the endpoint reachable only over your trusted LAN/VPN; the bridge never disables TLS verification.

python personal-bridge.py --config bridge-desktop.json

On Windows you can use py -3. Register a service/task appropriate to your OS if you want the bridge available after login/restart. The web application cannot install software on an unconnected laptop.

3. Connect actions in your assistant workspace

Choose Personal tools / local bridge, enter its HTTPS address, token and approved action ID. Add a short description of its inputs and effect. Use inspect_python for reading/assessing a tool project, stage_python on a server connection for transfer, and run_python_tool for a staged server tool. The environment verification uses the actual bridge response. Desktop connections cannot be enabled as independent automation.

4. Move a suitable Python tool

Ask your assistant to inspect a folder under one of the configured root IDs. Inspection parses source and dependencies without running the project. Windows/GUI/hardware dependencies, embedded secrets, unsafe packaging and missing configuration are surfaced for review. A candidate is not a proven compatible application.

For an eligible project, the assistant can package up to 100 small source/configuration files (500 KB total), verify their hash, and transfer them to the server bridge. Secrets, environments and dependency folders are excluded. Nothing in the project runs on the source laptop during this process.

5. Verify execution on the server

The server bridge requires Docker access and a preinstalled Python image. For standard-library tools, an operator can install python:3.12-slim once. Tools with third-party dependencies require an operator-prepared compatible image; dependencies are never installed on your laptop during assessment.

Server tests use a read-only, network-isolated container, a non-root user, bounded memory/CPU/processes and a timeout. Network, writable folders or hardware access must be provided through separately approved tool actions. A version is considered tested only after a real server result is returned. Verified server tool versions can then be pinned into an automation workflow.

Automation is independent of browser tabs

After a successful manual run, open Automation on that workflow. Set its interval, daily run limit and bounded Director budget, and approve any listed external effects. Different jobs have two bounded worker slots; repeated runs of one workflow never overlap. Missing input, changed connections or uncertain writes pause automation and notify your assistant.
